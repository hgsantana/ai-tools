# Using ai-tools

This guide is harness-agnostic. Skills are the user entry points. Automatic routing depends on the user-wide instructions being loaded; see [Supported harnesses](../README.md#supported-harnesses).

## Invocation

Invoke a skill explicitly by leading with its slash name and optional request:

```text
/az-ai-tools list costly idle resources
```

Skills provide session-directed workflows. Testing, interaction, and security protocols are provided across supported harnesses via user-wide instructions.

## Skills

| Skill | Use it for | Example |
|---|---|---|
| `/plan-ai-tools` | Formulate a user story as PO, writing its requirements into the spec, have a Planner subagent draft the general plan, then on approval orchestrate each task through a Task Planner that details it, a single-task implementer that delivers it, and an Evaluator that judges and commits it, then have an Acceptor check the whole branch against the spec, through to PR creation; with the slug of an existing plan it goes straight to orchestration | `/plan-ai-tools add user authentication` |
| `/vibe-ai-tools` | Refine a user story and its spec as PO interactively, then autonomously run planning, task implementation, validation, story acceptance, and PR creation | `/vibe-ai-tools add user authentication` |
| `/team-ai-tools` | Run the full team flow in one skill: PO story and spec, Architect plan, then per task a domain Specialist details and validates what an isolated implementer delivers, and a QA Specialist accepts the whole branch against the spec, through to PR creation | `/team-ai-tools add user authentication` |
| `/campaign-ai-tools` | Settle a campaign charter (work-point definition, done criteria, preserved behavior), then run unattended cycles in which a Planner scans the repository with the recorded recipe, plans one work point, drives and validates single-task implementers, and checks the work point against the criteria, until nothing is left to do | `/campaign-ai-tools raise unit test coverage of the domain layer` |
| `/audit-ai-tools` | Audit a repository read-only for defects, security flaws, and drift between code and its specs at `general`, `thorough`, or `exhaustive` package depth, orchestrating clean-context subagents to map perimeter and disjoint scopes, inspect code, adversarially refute or reproduce candidates in an isolated temp sandbox, and write a calibrated report | `/audit-ai-tools thorough` |
| `/az-ai-tools` | Inspect or manage Azure resources, subscriptions, infrastructure, and costs with `az` | `/az-ai-tools list costly idle resources` |
| `/gc-ai-tools` | Inspect or manage Google Cloud projects, infrastructure, and costs with `gcloud` | `/gc-ai-tools show resources in project-x` |
| `/stripe-ai-tools` | Inspect, integrate, and manage Stripe payments, Checkout Sessions, products, and webhooks | `/stripe-ai-tools integrate checkout session` |
| `/agy-ai-tools`, `/claude-ai-tools`, `/codex-ai-tools`, `/copilot-ai-tools` | Dispatch an agent by tier (`junior`, `mid-level`, `senior`) or explicit model and effort | `/claude-ai-tools senior review the auth module` |
| `/gh-ai-tools` | Inspect or manage GitHub accounts, repository administration, environments, Actions/builds, issues, and releases | `/gh-ai-tools show failing Actions runs` |
| `/update-ai-tools` | Preview update with dry-run, confirm destructive changes, and update across all harnesses | `/update-ai-tools` |
| `/remove-ai-tools` | Remove installed ai-tools artifacts from selected harnesses | `/remove-ai-tools claude-code and copilot` |

### Who does the work

Every skill runs on the session's model. The session handles user alignment, judgment, commits, and short pointers to disk; builds, tests, and bulk fact collection go to the harness's default subagent. In `/plan-ai-tools` the session is PO and orchestrator: it settles the story with the user, writing the requirements and their scenarios into spec files and the change into the story, one clean-context Planner questions what the spec leaves unverifiable and writes the general plan of architecture, constraints and verification commands, task separation, and requirement coverage, and after the implementation offer the session itself dispatches, for each task, one clean-context Task Planner to detail it, one single-task implementer to deliver it, and one clean-context Evaluator on the session's model and effort to judge the diff scenario by scenario against the spec, the plan, and the task file, adversarially hunting for bugs, edge cases, misuse, security flaws, and scope gaps beyond the expected behavior, and commit approved work; the Evaluator ends with its task. Once every task is done, a clean-context Acceptor judges the whole branch against the spec and sends gaps back through the task loop as convergence tasks, for at most two rounds. The session only branches on return signals, asks the user when a task blocks after 3 attempts or the story stays unaccepted, and opens the pull request, which carries the acceptance table. `/team-ai-tools` is the robust alternative for the same story: an Architect plans and assigns each task to one of nine domain Specialists, who details it and adversarially validates the implementer's delivery against the spec, and a QA Specialist accepts the whole branch, under `docs/team-ai-tools/<slug>/` on branch `team/<slug>`. In `/vibe-ai-tools`, the session refines the story interactively with the user and then takes full autonomous ownership of subsequent technical decisions—favoring zero-cost and easily reversible choices—approving the Planner's general plan itself against its coverage table and then running the same per-task cycle of Task Planner, implementer, and Evaluator and the same story acceptance through to PR creation, amending the spec itself when a requirement cannot hold and listing every amendment in the pull request, with one autonomous recovery before asking the user about a blocked task or story, under `docs/vibe-ai-tools/<slug>/` on branch `vibe/<slug>`. Every skill is self-contained and cites no other skill. In `/campaign-ai-tools`, the session only settles the campaign charter (work-point definition and search recipe, done criteria, preserved behavior, verification commands) and implementer with the user, dispatches one clean-context Planner per cycle, and makes the first and last commits on the local `campaign/<slug>` branch; each Planner follows the recorded scan, plans, dispatches implementers, adversarially validates, checks the work point against the done criteria, and commits, and the session never reads or judges a delivery. The campaign has no cycle cap: it stops only after 2 consecutive Planners find nothing left to do or when a Planner cannot dispatch the implementer, and aborts with the campaign state left in place when a Planner returns without a signal; the branch is never pushed.

These four skills implement with the harness default subagent without asking. Name another implementer in the request to override it: `session-subagent`, or a tier (`junior`, `mid-level`, `senior`) optionally prefixed by a harness, `agy`, `claude`, `codex`, or `copilot`, as in `/plan-ai-tools add user authentication, implement with agy junior`. A tier without a harness takes the current one; a tier of another harness is dispatched through that harness's CLI, and the skill stops when the CLI is unavailable. Every implementer lives for one delivery attempt: rework, a retry after a stop or a block, and a resumed task each go to a fresh implementer that continues from the task file and the uncommitted worktree, so a CLI dispatch behaves like a subagent one.

In `/audit-ai-tools`, the session settles the specialization depth (`general` for master packages up to 4,000 LOC per scope, `thorough` for direct subpackages up to 1,800 LOC per scope, or `exhaustive` for leaf sub-subpackages up to 800 LOC per scope, slicing scopes exceeding the mode ceiling and shallow flat packages over 400 lines into cohesive virtual subpackages) and orchestrates read-only discovery and verification without inspecting code itself: a Mapper documents global perimeter defenses, architectural invariants, specification sources, local verification toolchains, and a 100%-coverage disjoint scope manifest (including operational runbooks), bounded waves of Scope Auditors record single-fix atomic verbatim-backed candidates while checking sibling/CRUD symmetry and conformance to the specification sources and extrapolating outward only to verify in-scope hypotheses, a Clusterer enforces single-fix atomicity and deduplicates root causes into toolchain-grouped batches, Adversarial Verifiers attempt to falsify batches via full-function call-chain checks and isolated `${TMPDIR:-/tmp}/ai-tools` sandbox reproductions, and a Consolidator writes the five-tier topology-calibrated report (`docs/audit-ai-tools/<slug>/audit-<slug>.md` by default, uncommitted), whose remediation work packages state the expected behavior, the invariants to preserve, and the check that proves each fix, and verifies repository integrity. Mapper, Clusterer, Verifiers, and Consolidator inherit session model and effort; Scope Auditors default to `session-subagent` (also inheriting session model and effort) and accept `harness-default` or any harness tier override.

### Living spec

`/plan-ai-tools`, `/vibe-ai-tools`, and `/team-ai-tools` are spec-driven. Requirements live in spec files, one per capability, in the spec directory the repository keeps (`docs/specs/` by default, or its own): each requirement is one sentence of observable behavior with Given/When/Then scenarios and a stable ID. A story edits those files in place on its branch, so the branch diff of the spec is the change, and the spec survives delivery while story, plan, and task files are removed. When the repository keeps no spec directory, the PO asks once whether to keep one; if declined, the spec lives in the plan directory and is removed with it. Outside the skills, the user-wide `living-spec` rule keeps the spec current, and `/audit-ai-tools` reports drift between a spec and its code.

### Agent dispatch

`/agy-ai-tools`, `/claude-ai-tools`, `/codex-ai-tools`, and `/copilot-ai-tools` each hold their harness's tier table. They dispatch through the CLI when installed, else through the harness subagent API with the tier's model and effort, else with the closest model and effort that API offers, and report which level and substitution applied. The same tier tables serve implementers requested in other skills, including a tier of another harness, dispatched through its CLI.

### Cloud and platform tools

`/az-ai-tools`, `/gc-ai-tools`, `/gh-ai-tools`, and `/stripe-ai-tools` run read-only queries freely. Every mutation is presented separately with its target, reason, and cost or blast-radius impact, and requires explicit approval for that action.

`/gh-ai-tools` is for GitHub-hosted state and administration: accounts, organizations, repository settings and access, environments, secrets and variables, Actions, builds, artifacts, issues, and releases. Repository code work—commits, branches, tags, cherry-picks, rebases, merges, fetches, pulls, pushes, code review, and pull-request creation, updates, review, or merge—runs directly in the session without this skill. Platform policy such as rulesets, required checks, and pull-request settings remains in scope for the skill.

### Maintenance

`/update-ai-tools` runs `"$HOME/.ai-tools/scripts/shell/update.sh"` across all supported harnesses with `--overwrite`, `--harnesses all`, and `--discard-local`. It runs `--dry-run` first without questions, presents what will be lost or overwritten, and asks for confirmation before executing. `/remove-ai-tools` runs `"$HOME/.ai-tools/scripts/shell/remove.sh"`: first settle harness scope, run with `--dry-run`, and present destructive flags separately. Both resolve the canonical clone first, do not run relative scripts from the caller's project, and leave `$HOME/.ai-tools/USER-AGENTS.md` untouched. An approved `--purge` writes dry-run, execution, and final reports under `$HOME/.ai-tools-remove-logs` so evidence survives deleting the clone.

First installation is not a skill: follow the root `README.md` installation process.
